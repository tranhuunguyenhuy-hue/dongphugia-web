# V1 CI/CD fast lane

One branch and one PR per issue. Policy: [AGENTS.md](../../AGENTS.md); live state is verified in Cloudflare/GitHub Actions, not in a status file. No parallel deployment paths; Production deploys are serialized and need Owner approval.

1. **Verify** affected source with focused tests, typecheck/build and PR. Required GitHub status: `quality`; documentation-only changes skip expensive application checks, but code, test and workflow changes must pass the actual required checks. The PR gate prints the computed risk lane floor.
2. **After merge (automatic, #505)**: a successful `quality` push on `main` triggers, through an unprivileged gate job that re-checks repository/ref/event/actor/conclusion and that the SHA is still `main` HEAD, and only when the **cumulative** lane live Production → head is `fast`, `standard` or `extended` (a pending SQL/function/binding change, or an UNKNOWN scope, keeps every later push out; multi-commit pushes are covered):
   - `v1-fixed-preview.yml` `publish-m3` to fixed Staging, unless superseded or a UAT lock is held (skipped with the reason in the summary);
   - `m4-production-admin-release.yml` `verify`: packaged Worker against the Production DB read-only, no media test object. It never publishes.
3. **Owner UAT** on Staging for every runtime lane (fast: a short check, or an explicit Owner waiver). An auto publish is **not** protected: before handing UAT, dispatch `v1-fixed-preview.yml` `operation=lock-uat` with `uat_issue` (pins the newest Staging deployment when it carries this SHA tag and the combined publisher's `M3 Admin <sha>` message; no redeploy; content hashes are not compared) or `publish-m3` with `uat_issue`. Every Staging writer (`publish-m3`, `lock-uat`) runs in the `m2-fixed-staging` group, checks the lock in the gate and again right before writing, and refuses an older or superseded SHA. While locked, only the holder may redeploy, and only the locked SHA. The legacy M2 `publish` (Public-only artifact under the same SHA tag) is **disabled** (archival #510); re-enable only by a reviewed PR with Owner approval. **Recovery**: a label without exactly one valid `STAGING-UAT-LOCK <sha>` line, an edited lock comment, or two labelled issues, blocks every Staging write; the holder or Owner removes the label once the UAT verdict is recorded (never automatic), then locks again. A manual run that GitHub cancels while pending behind another Staging run is simply dispatched again.
4. **GO and publish** only with `.github/workflows/m4-production-admin-release.yml` `operation=publish` from reviewed `main`. Every manual dispatch (verify, publish, Staging) needs a successful `quality` push run on `main` for the exact SHA. The verify summary shows **READY** (this run may be cited as `VERIFY-RUN`; it is not UAT or GO) only when the run, flags, live state, scope and `quality` all passed, and only then prints the GO template and the inputs `approved_source_sha`, `rollback_version_id` (active version = rollback target) and `go_comment_url`. The GO comment (Owner, unedited, open release issue, column-0 directives) carries:
   - `GO-PROD <sha>` and `VERIFY-RUN <id>` — a trusted verify operation of that SHA that built the reviewed flags file, finished before the GO and not followed by a failed verify;
   - `LANE <lane>` for extended/full;
   - `UAT PASS <sha>` posted while fixed Staging served exactly that SHA from the combined `publish-m3` job (a later `UAT FAIL`, even edited, cancels it), or `UAT-WAIVER <sha> <reason>`;
   - `FLAGS-CHANGE …` only when the reviewed flags differ from the active version.
   The lane checks all of this before building and again right before deploying, together with `quality`, `main` HEAD and the rollback target. A release scope with real **SQL, Supabase function or Worker binding** changes (or an UNKNOWN scope) is refused by this Worker-only lane (`FULL_SCOPE_REQUIRES_PROTECTED_FULL_PROCESS`): no existing lane evidence yet proves which operation ran and that every required change holds, so escalate to Owner/TL under the existing protected full process (`m6-production-sql-apply.yml`, `m4-production-function-deploy.yml`, backup). Flags come only from `release/production-flags.json`; the deployed version must match it.
5. **Do not** use `v1-worker-release.yml` (refuses to publish while Production carries the Admin), the M2 `v1-fixed-preview.yml` snapshot lane (recovery/staging only), or any publish of a snapshot/Public-only artifact over the Admin. Do not change DNS or Production settings to make a check pass.
6. **Record** in the assigned issue: the run links (the summary already holds SHA, scope, flags, active/rollback version, deployed version), real live smoke, PASS/FAIL/UNKNOWN. Worker rollback does not restore SQL.

- Worker `dongphugia-v1-public-production` serves canonical Public plus the accepted Admin under `/admin-next`; legacy `/admin*` redirects (302). Edge Function `admin-api` runs on Production `bonxyxluzlxfkdetryoo` (`production_writes_allowed = true`, migrations `001`/`002` applied). - Rollback order: Worker `wrangler rollback <previous version>` (does not undo SQL) → delete the function → revoke banner grant/policy → `002`/`001` rollbacks; restore from backup only for data loss. Detail: [M4 Admin plan](../deploy/m4-production-admin-plan.md).
- Backup: `.github/workflows/m4-production-backup.yml` daily 19:41 UTC with an encrypted restore rehearsal; see the [backup runbook](m5-backup-recovery-runbook.md). Media/CDN state and rollback ledgers: [CDN normalization](m5-legacy-cdn-normalization-plan.md).
