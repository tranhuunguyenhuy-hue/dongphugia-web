## Workflow
1. **Start**: `git status --short --branch`, fetch, compare with `main`, read the issue's latest comments. Do not discard WIP or restart finished work. If a cloud app created its own branch, keep the branch ancestry and name the continuation branch.
2. **Branch/PR**: one branch and one PR per issue, named `codex/<issue>-<slug>` or `claude/<issue>-<slug>`. Declare in the issue which files you will touch so parallel lanes do not collide. Rebase or merge `main` before opening the PR.
3. **Verify**: run affected tests, typecheck/build and, when applicable, a real hosted smoke. Node 24.13.0, npm 11.6.2, committed lockfiles. Required CI status: `quality` (`.github/workflows/quality.yml`); the docs-only classifier is not a bypass for source changes. On repeated failure change approach and report the exact blocker. Do independent safe work instead of waiting on CI.
4. **Self-review and merge**: the implementing agent inspects its exact diff and file list, confirms scope and safety, runs the required CI on the exact head, then **self-merges when every objective gate passes**; it records the commit SHA and PASS / FAIL / UNKNOWN evidence in the issue. Do not stop to ask for routine Tech Lead LGTM or merge permission. **Docs/CI/maintenance without runtime change**: self-merge after required CI and scope checks; do not deploy anything just to satisfy process. **Runtime/UI changes**: deploy to the fixed staging through the existing protected workflow and hand the Owner a stable staging URL, SHA and UAT checklist; the Owner gives final UAT. A green CI, merge or deployment record alone is never Production acceptance. While acceptance or a decision is pending, continue the next independent, already-approved task without polling or spawning threads.
5. **Release**: Production deploys are **serialized** (one at a time, **explicit Owner approval**, exact approved SHA, post-deploy smoke, rollback plan) because Public and Admin share one Worker. Use only the reviewed lane in the handbook; never publish a stale or Public-only artifact over the Admin; do not dispatch unrelated legacy workflows; do not bypass identity gates or change protected settings to turn CI green. If an actor or scoped credential is missing, state the exact Owner action.
6. **Before hosted writes** confirm target, backup + restore/rollback, schema/permissions, free quota, non-sensitive seed and existing consumers. Worker rollback and PostgreSQL rollback are separate; Worker rollback does not undo SQL.
7. **Handoff** (before stopping or switching agent): commit, push, verify the SHA, then comment in the issue: branch/SHA, completed work, PASS/FAIL/UNKNOWN, next concrete command or blocker, deployment/version if applicable, backup status, Owner action. Never claim local-only state transferred. No merge or deploy solely for handoff. Keep reports short.
8. **Stop only for** a material business/scope/architecture choice, an exclusive Owner/Tech Lead action or credential, unreconciled potentially destructive impact, a security issue, real Production/backup/recovery risk, or a CI/release check that cannot be fixed safely within scope. Report one concrete decision or action, the evidence, and the independent work that continues. Self-merge never permits bypassing CI, expanding scope, deleting unrelated resources or deploying to Production.
